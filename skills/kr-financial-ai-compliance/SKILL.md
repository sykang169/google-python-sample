# 금융권 AI 가드레일

> [!IMPORTANT]
> **이 문서는 법률 자문이 아니다.** 규제는 개정되고, 업권(은행/증권/보험/여전)과
> 상품에 따라 적용이 다르다. 여기 있는 것은 엔지니어링 기본선이며,
> 실제 배포 전 **준법감시인·법무 검토가 반드시 필요하다.** 그 사실을 설계
> 산출물에도 명시한다.

금융권에서 AI가 사고를 내는 지점은 모델 성능이 아니라 거의 항상
**경계**다 — 안내인지 권유인지, 공개정보인지 신용정보인지, 로그에 남겨도
되는지. 아래 다섯 가지를 설계 단계에서 정한다.

## 1. 안내 vs 투자권유

가장 자주 넘는 선이다. 금융소비자보호법과 자본시장법은 "정보 제공"과
"권유"를 다르게 다루고, 권유에는 적합성 원칙과 설명의무가 따라붙는다.

| 해도 되는 것 (정보 제공) | 넘어가는 것 (권유로 읽힘) |
| --- | --- |
| 조회한 시세·금리·재무 수치를 출처와 함께 제시 | "지금 사세요", "이 상품 가입하세요" |
| 여러 상품·종목을 같은 기준으로 비교 | 특정 상품 하나를 콕 집어 추천 |
| 공시된 사실과 계산식을 설명 | 목표주가, 상승/하락 전망 단정 |
| 위험 요인을 함께 안내 | "원금 손실 없습니다", "확정 수익" |
| "판단은 고객님께서" 라고 남김 | 사용자의 재산 상황을 모른 채 적합성 판단 |

구현 규칙:

- **수익률·금리를 제시할 때 위험과 조건을 같은 화면에 둔다.** 유리한 정보만
  강조하고 불리한 정보를 생략하는 것 자체가 문제가 된다.
- 과거 데이터의 설명과 미래 예측을 문장에서 분리한다. 예측을 요구받으면
  "예측이 아니라 과거 추이"라고 밝히고 그 범위 안에서 답한다.
- 원금 손실 가능 상품(주식, 펀드, ELS, 변액보험 등)이 언급되면
  **투자 위험 고지를 자동으로 덧붙인다.** 사람이 기억해서 붙이는 구조로 두지 않는다.
- 확정적 단정 표현(반드시, 확실히, 무조건, 손실 없음)을 출력 검증에서 걸러낸다.

세부 조문과 업권별 차이는 [references/regulations.md](references/regulations.md)를 읽는다.

## 2. 개인정보 · 개인신용정보

금융권에서는 개인정보보호법 위에 **신용정보법**이 더 얹힌다. 계좌번호, 카드번호,
거래내역, 신용점수, 대출 잔액은 개인신용정보이고 취급 기준이 더 엄격하다.

설계 기본선:

- **프롬프트에 원본 식별정보를 넣지 않는다.** 주민등록번호, 계좌번호,
  카드번호는 모델에 보내기 전에 토큰으로 치환한다. 필요한 것은 대개
  "이 사람의 잔액"이지 "이 계좌번호"가 아니다.
- **로그·트레이스에 PII가 새지 않게 한다.** LLM 관측 도구는 프롬프트 전문을
  저장하는 것이 기본 동작이다. 저장 전에 마스킹하거나 저장을 끈다.
  이 항목은 사고가 나면 가장 크게 번지는 곳이다.
- **목적 외 이용을 만들지 않는다.** 수집 목적과 다른 용도로 쓰려면 별도 동의가
  필요하다. "이왕 있으니 학습에 쓰자"가 대표적인 위반 경로다.
- **모델 학습에 고객 데이터를 넣기 전에 멈춘다.** 가명처리·동의·위탁 구조를
  법무와 정리하기 전까지는 진행하지 않는다.
- 대화 이력에 남은 PII의 **보존 기간과 파기 절차**를 처음부터 정한다.

## 3. 감사 추적

금융 규제는 "왜 그렇게 답했는가"를 사후에 재현할 수 있기를 요구한다.
설명의무 이행 기록 등은 **장기간 보존**해야 하므로, 로그 스키마를
나중에 붙이면 이미 늦다.

에이전트 한 턴마다 최소한 이만큼 남긴다:

| 필드 | 이유 |
| --- | --- |
| 요청 ID · 세션 ID · 타임스탬프(KST) | 재현의 기준점 |
| 사용자 식별자 (가명화된 값) | 원본 식별자를 그대로 넣지 않는다 |
| 모델 ID와 버전 | 같은 프롬프트도 모델이 바뀌면 답이 바뀐다 |
| 호출한 도구와 파라미터 | 어떤 데이터에 근거했는지 |
| **데이터 출처와 기준시점** | "2026-08-31 기준 공시" 처럼 |
| 최종 응답 원문 | |
| 적용된 가드레일과 차단 사유 | 필터가 동작했다는 증거 |
| 사람 검토 여부와 검토자 | |

보존 기간은 업권·업무별로 다르다. 기본을 길게 잡고 법무 확인 후 줄인다.

## 4. 인프라 제약

- **망분리.** 전자금융감독규정은 전산실·내부망 분리를 요구한다. 외부 LLM API
  직접 호출이 막히는 환경이 흔하므로, 프록시·전용선·승인된 클라우드 구간을
  전제로 설계한다. "일단 공용 API로 만들고 나중에 옮기자"는 대개 다시 만들게 된다.
- **데이터 레지던시.** 국내 리전을 기본으로 둔다. Google Cloud는
  `asia-northeast3`(서울)이다. 모델 호출 리전, 로그 저장 위치, 벡터 DB 위치를
  각각 확인한다 — 하나만 국외면 전체가 국외 이전이 된다.
- **클라우드 이용 절차.** 금융회사의 클라우드 이용에는 안전성 평가와 감독당국
  보고 절차가 따른다. 리소스를 만들기 전에 이 절차의 진행 상태를 확인한다.
- **제3자 위탁.** 외부 모델 제공자는 처리 위탁 대상이다. 계약·평가·감독 의무가
  붙으며, 여기에는 "입력 데이터를 학습에 쓰지 않는다"는 확인이 포함된다.

## 5. 사람이 반드시 개입하는 지점

다음은 모델이 최종 결정하지 않는다. **자동 실행 대신 초안 + 사람 승인** 구조로 만든다.

- 대출 승인·거절, 한도·금리 결정
- 보험 인수 거절, 보험금 지급 결정
- 계좌 개설·해지, 송금·이체 실행
- 고객 등급 강등, 거래 제한, 이상거래 차단 확정
- 고객에게 나가는 확정적 상품 권유
- 규제기관·감독당국 제출 문서

거절·불이익 처분에는 **설명 가능한 사유**가 필요하다. 근거를 재현할 수 없는
모델 출력만으로 불이익을 결정하지 않는다.

## 설계 체크리스트

금융권 에이전트를 만들 때 이 순서로 확인하고, 답하지 못한 항목은
**모른다고 표시해 사용자에게 남긴다.** 빈칸을 임의로 채우지 않는다.

```markdown
### 규제 체크리스트
- [ ] 이 기능은 정보 제공인가, 권유인가? (권유면 적합성·설명의무 설계 필요)
- [ ] 원금 손실 가능 상품을 다루는가? → 위험 고지 자동 삽입
- [ ] 개인신용정보가 프롬프트에 들어가는가? → 마스킹/토큰화
- [ ] 로그·트레이스에 PII가 저장되는가? → 저장 전 마스킹
- [ ] 감사 로그에 출처·기준시점·모델버전이 있는가?
- [ ] 모델 호출/로그/DB가 모두 국내 리전인가?
- [ ] 자동 실행되는 불이익 결정이 있는가? → 사람 승인으로 전환
- [ ] 데이터 보존 기간과 파기 절차가 정해졌는가?
- [ ] 준법감시인 검토를 받았는가?  ← 배포 전 필수
```

## 응답에 붙이는 고지

금융 수치를 답할 때 마지막에 붙인다. 상황에 맞게 줄이되 출처와 기준시점은 뺀다.

```markdown
---
- 출처: [기관·서비스명], 기준시점 [YYYY-MM-DD]
- 본 내용은 정보 제공 목적이며 투자권유나 금융상품 가입 권유가 아닙니다.
- 투자에는 원금 손실 위험이 있으며, 실제 조건은 금융회사·개인 신용도에 따라 다릅니다.
```

## 사용자가 선을 넘는 요청을 할 때

"어디에 투자하면 돼?", "이거 사도 돼?" 같은 요청은 자연스럽고, **거절이 답이
아니다.** 할 수 있는 것으로 바꿔 준다.

1. 요청의 사실 부분에는 데이터로 성실히 답한다 (시세, 금리, 재무, 비교)
2. 판단 부분은 기준을 제시하는 방식으로 바꾼다 —
   "무엇을 사야 하는지"가 아니라 "무엇을 보고 판단하는지"
3. 개인 상황에 따라 달라지는 부분은 전문가·창구 상담으로 연결한다

설교하지 않는다. 한 문장으로 경계를 밝히고 바로 도움이 되는 내용을 준다.
