# 기업 재무·공시 분석 (금융위)

DART와 **겹치는 영역**이다. 어느 쪽을 쓸지 먼저 정하는 것이 이 스킬의 첫 일이다.

## DART와 이 서버, 무엇을 쓰나

| 필요한 것 | 쓸 곳 |
| --- | --- |
| 계정 값으로 **계산**(부채비율, 성장률, 피어 비교) | **여기.** 정규화된 표라 바로 계산된다 |
| 여러 기업·여러 연도를 한 번에 훑기 | **여기.** `crno`·`bizYear` 필터로 스캔 |
| 공시 **원문**, 사업보고서 본문, 첨부문서 | [DART](../dart-disclosure-analysis/SKILL.md) |
| XBRL 상세 계정, 주석 | [DART](../dart-disclosure-analysis/SKILL.md) |
| 2015년 이전 데이터 | 여기 (DART는 2015년 이후만) |

**같은 회사의 같은 항목이 두 소스에서 다를 수 있다.** 작성 기준과 정정 반영
시점이 다르기 때문이다. 한 답변 안에서 두 소스의 수치를 섞지 않는다.
섞어야 한다면 어느 값이 어디서 왔는지 행마다 밝힌다.

## 핵심 규칙

1. **법인등록번호(`crno`)가 열쇠다.** 회사명으로는 조회되지 않는다.
   `get_corp_outline`으로 먼저 확정한다 —
   [kr-entity-resolution](../kr-entity-resolution/SKILL.md).
   DART의 `corp_code`(8자리)와는
   **다른 식별자**이므로 서로 넘기지 않는다.
2. **연결/별도를 확인한다.** 재무제표 응답의 `fnclDcd`가
   `FS_ifrs_Consolidated`(연결) / 개별을 구분한다. 어느 쪽인지 밝히지 않은
   수치는 그 자체로 틀린 답이다.
3. **공시는 33종의 오퍼레이션으로 나뉜다.** 배당은 `getDiviDiscInfo_V2`,
   합병은 `getMnaDiscInfo_V2`, 자기주식 취득은 `getTreaStocRepuDiscInfo_V2`처럼
   사안마다 다르다. **이름을 추측하지 말고** `search_apis`로 찾는다.

## 워크플로

```
get_corp_outline({"crno": ...} 또는 회사명 필터)  → crno 확정
        ↓
get_financial_statement({"crno": ..., "bizYear": "2025"})   재무상태표
search_apis("손익")  → getIncoStat_V2 / getSummFinaStat_V2
        ↓
get_affiliates / search_apis("공시")로 사안별 공시
```

## 재무 지표 계산

계산에 쓴 계정과 기간을 항상 함께 표기한다.

| 지표 | 식 | 주의 |
| --- | --- | --- |
| 부채비율 | 부채총계 / 자본총계 × 100 | 자본잠식(≤0)이면 계산하지 말고 "자본잠식"으로 보고 |
| 유동비율 | 유동자산 / 유동부채 × 100 | 금융업은 의미가 없다 |
| 영업이익률 | 영업이익 / 매출액 × 100 | 매출 0이면 계산 불가 |
| ROE | 당기순이익 / 자본총계 × 100 | 단일 시점 값이면 그렇게 밝힌다 |

> [!CAUTION]
> **은행·보험·증권은 위 지표를 그대로 쓰면 안 된다.** 부채가 곧 예수금인
> 업종이라 부채비율 1,000%가 정상이다. 업권 지표(BIS, NIM, 지급여력)는
> [kr-securities-industry-benchmark](../kr-securities-industry-benchmark/SKILL.md)의
> 금융회사 통계를 쓴다.

## 공시를 다룰 때

공시는 **사건**이다. 조회 결과가 0건이면 "그런 일이 없었다"가 아니라
"이 오퍼레이션 기준으로 잡히지 않았다"이다. 배당이 없는 게 아니라 배당 공시
오퍼레이션을 잘못 골랐을 수 있다. 0건일 때는 `search_apis`로 인접한 공시
오퍼레이션을 한 번 더 확인한 뒤에 답한다.

## 도구를 고르는 순서

```
이름 있는 도구로 되는가?  →  그걸 쓴다
       ↓ 아니면
search_apis("검색어")     →  service · operation · fields 확인
       ↓
call_api(service, operation, params)
```

`search_apis`가 돌려주는 `fields`가 **그 오퍼레이션의 응답 필드이자 필터
파라미터**다. 금융위 API는 응답 필드명을 그대로 쿼리 파라미터로 받는다.
이 목록은 실제 호출로 수집한 것이라 문서와 어긋나지 않는다.

파라미터를 기억해서 쓰지 않는다. 필드명을 지어내면 조용히 무시되어
**필터가 걸리지 않은 전체 결과**가 돌아온다 — 오류가 아니라 잘못된 답이 된다.

## 자주 쓰는 필터

| 필드 | 뜻 |
| --- | --- |
| `basDt` | 기준일자 `YYYYMMDD` (하루) |
| `beginBasDt` / `endBasDt` | 기간 조회 |
| `itmsNm` / `likeItmsNm` | 종목명 정확 일치 / 부분 일치 |
| `isinCd` / `crno` | ISIN·법인등록번호 — 확정 방법은 [kr-entity-resolution](../kr-entity-resolution/SKILL.md) |
| `basYm` | 기준월 `YYYYMM` (통계 계열) |

## 오류 코드

금융위 API는 **HTTP 200과 함께** `resultCode`로 결과를 준다. 코드마다 다음에 무엇을
할지는 **도구가 오류 메시지에 함께 실어 보낸다.** 그 지침을 따르고, 코드를 "조회
실패"로 뭉뚱그리지 않는다 — `03`은 다시 물어야 하고 `30`은 재시도가 무의미하다.

## 상류가 막혔을 때

금융위 API는 짧은 시간에 호출이 몰리면 **소스 IP 단위로 접속을 수 분간 막는다.**
그때는 도구가 다음 형태로 답한다.

- `apis.data.go.kr에 연결하지 못했습니다` — 연결 자체가 막혔다
- `연결이 반복 실패해 N초 동안 호출을 멈춥니다` — 서버가 회로를 닫아 상류를 쉬게 하는 중

둘 다 **데이터가 없다는 뜻이 아니다.** 사용자에게 "지금 조회할 수 없다"고 알리고,
기억이나 웹 검색으로 수치를 채우지 않는다. 잠시 후 다시 시도하면 된다.

같은 조회를 반복하지 않는다. 서버가 응답을 캐시하므로 정상일 때는 반복 조회가
저렴하지만, 막힌 상태에서 재시도를 반복하면 차단이 길어진다.

## 시점을 반드시 밝힌다

> [!CAUTION]
> **이 데이터는 실시간이 아니다.** 금융위 제공 서비스는 기준일 다음 영업일
> 13시 이후에 갱신된다. 오늘 날짜로 조회해 데이터가 없는 것은 정상이다.

숫자를 인용할 때는 항상 **출처 · 기준일 · 단위**를 함께 쓴다.

휴장일 처리, "최근"을 구간으로 바꾸는 법, 기간 계산의 함정은
[kr-market-calendar](../kr-market-calendar/SKILL.md)에 있다.
값은 전부 문자열이므로 계산 전에 숫자로 바꾸고, 빈 문자열은 0이 아니라 결측이다.

## 이 서버가 다루는 API

7종 · 오퍼레이션 45개. 전부가 도구로 나와 있지는 않다 — 나머지는
`search_apis`로 연다.

| 서비스 | 이름 | 오퍼레이션 |
| --- | --- | --- |
| `GetESGIdxInfoService` | ESG지수정보 | 1 |
| `GetDiscInfoService_V2` | 공시정보 | 33 |
| `GetFinaStatInfoService_V2` | 기업 재무정보 | 3 |
| `GetCorpBasicInfoService_V2` | 기업기본정보 | 3 |
| `GetCGDiscInfoService` | 기업지배구조 공시정보 | 3 |
| `GetStkIssuInfoService` | 주식발행 공시정보 | 1 |
| `GetCorpGoveInfoService` | 지배구조정보 | 1 |

- 실시간인 것처럼 말하지 않는다. 기준일을 항상 명시한다.
